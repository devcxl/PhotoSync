# 通用 PTP 事件通道（中断端点 + 标准事件包）值不值得做

**日期**: 2026-11-16
**状态**: 调研（对应 GitHub issue #10）

> 范围声明：本文只回答「值不值得做、受什么约束」，不设计功能、不改代码。
> 规范引用一律给出条款号与印刷页码；代码引用统一取自 libgphoto2 2.5.34 发布包
> （与仓库已装的 `libgphoto2 2.5.34` 对应）以及 `master` 的机型转储，格式 `文件:行号`。
> 二手来源（博客、StackOverflow、第三方仓库）在正文显式标注「二手」，且不参与结论推导。

---

## 1. 结论摘要

1. **事件能力本身是强制的**：PIMA 15740:2000 §12 开篇即 "Event support shall be mandatory."
   （p.79）；USB 传输上事件的唯一标准通道就是 interrupt endpoint（Annex D.4.3 要求设备
   "shall contain ... an Interrupt endpoint"，D.4.3.4 规定它 "shall be used to send event data"）。
2. **但「机身自己拍的新照片一定发 `0x4002`」在 1.0 里没有逐字条款**。标准只对
   *主机触发* 的 `InitiateCapture` / `InitiateOpenCapture` 明确要求逐对象发 `ObjectAdded`
   （§10.4.14 p.59–60、§10.4.28 p.69–70）。对本地拍摄，标准给的是「能力声明」
   （`DeviceInfo.EventsSupported`，p.16）加一个「我可能漏报，你自己重同步」的兜底事件
   `UnreportedStatus`（§12.5.14，p.86）。
3. **「轮询 GetEvent」这个前提需要修正**：PTP 1.0 全文没有 `GetEvent` 这个操作（全文检索 0 次命中），
   libgphoto2 与 libmtp 也都没有标准 `GetEvent` 的 opcode。业界口里的 "GetEvent" 全是**厂商私有 RPC**：
   Nikon `0x90C7`/`0x941C`、Canon EOS `0x9116`、Canon 消费机 `CheckEvent`、Panasonic `0x9603`。
   所以不存在「标准 GetEvent 轮询」这条路，也就谈不上「用轮询替代中断」。
4. **libgphoto2 的通用路径确实读中断端点**：`ptp_check_event`（`ptp.c:3533`）在排除了 Nikon/Canon
   私有分支后走到 `params->event_check`（`ptp.c:3596`），即 `ptp_usb_event` → `gp_port_check_int`
   （`usb.c:546-561`），并把读到的包直接当事件容器解析（`usb.c:598-606`）。`0x4002` 在这里被翻译成
   `GP_EVENT_FILE_ADDED`（`library.c:7445`）。
5. **机型分布既不是「普遍支持」，也不能按品牌一概而论**：libgphoto2 `master` 里 288 份可解析的
   `DeviceInfo` 转储中，221 份（76.7%）声明 `0x4002`。**Sony 只有 2/35**；Canon 整体 88/106，
   但**按代际分裂**：老 EOS（5D Mark II、7D、60D、600D 等）27/43 声明，新世代 EOS
   （R 系、M50 及之后、80D/90D、6D Mark II、5D Mark IV）16 台**全部不声明**，PowerShot 47/49 声明。
   声明 `0x4002` 的厂商里，Nikon 有 25 个 Coolpix 型号被上游标记为「根本不发 ObjectAdded」。
6. **结论**：值得做，但只能定位为「事件通道 + 厂商适配层」的**低优先兜底**，不能作为
   「通用拍照通知」的承诺；对 Canon EOS / 现代 Sony 做这条通道是纯成本。是否值得落地取决于
   目标机型抽样（见 §6 的判定实验）。

**置信度**：规范条款 高（原文逐条核对）；实现路径 高（源码）；机型分布 中高
（上游转储是能力声明，不等于运行期行为）；「机身本地拍摄是否发 0x4002」低（无公开系统数据，
仅有个例日志与上游注释）。
**未能验证**：ISO 15740:2008 / 2013（PTP 1.1 及第三版）正文是否新增了标准 `GetEvent`——
正文付费，公开样本只到第 7 页，不含操作码表。

## 2. 规范怎么说

### 2.1 事件是强制的，但「通道」由传输层定义

PIMA 15740:2000 §12（p.79）原文：

> This section describes events, their datasets, and their usages. **Event support shall be
> mandatory.**

同节 §12.1.2（p.79）把「带外事件」定义为「传输层另有一条逻辑连接」：

> Transports that use a separate logical connection for interrupts effectively have support for
> out-of-band events. This support means that such transport implementations will not need to
> break up long image transfers into smaller data blocks …

ISO 15740:2008（PTP 1.1）保留了同一立场：Clause 4 导语（p.6）"The use of events is mandatory in order to
ensure synchronization between devices."；§4.2.5 同页（p.6）"The DSPD shall be capable of generating and
reacting to asynchronous events."

### 2.2 USB 传输：中断端点是「必备端点」，不是可选优化

PIMA 15740:2000 Annex D.4.3（p.117）：

> The device **shall** contain at least four endpoints: default, Data-In, Data-Out, and an
> Interrupt endpoint.

D.4.3.4（p.118）：

> The Interrupt endpoint associated with the Still Image Interface **shall be used to send event
> data** to the host from the device. … The direction shall be IN.

USB-IF《Still Image Capture Device Definition》rev 1.0（下称 SICDD）§4.3 复述同一要求，
§7.3 进一步把「通知能力」写成合规条件：

> A Still Image Capture Device that is compliant to PIMA 15740 **shall provide a means to notify
> the host** of the occurrence of certain events. … A USB Still Image Capture Device uses the
> **interrupt endpoint** associated with the Still Image Interface for this purpose.

SICDD §7.3.1 给出的 interrupt 数据格式与 PIMA Annex D.7.3.1（p.142）一致：12 字节头
（`Interrupt Data Length` / `Container Type = 0x0004` / `Event Code` / `TransactionID`）+ 最多 3 个
4 字节参数，参数个数 = `(Length - 12) / 4`。

补充：SICDD §5.2.2 还定义了一个 **class-specific 控制请求** `Get_Extended_Event_Data`
（`bRequest = 0x65`），但它不是「拉取事件队列」，而是「已经收到某个中断事件后，去取该事件的
附加数据」，且是 **may accept**（可选）。这一点很重要——它常被误读成「标准 GetEvent」。

### 2.3 `DeviceInfo.EventsSupported` 的精确含义

PIMA 15740:2000 §5.5.1 Table 6（p.16），第 7 个字段，`EventCode Array`，说明原文：

> **EventsSupported**: This field is an array of EventCodes representing the events that are
> **currently generated by the device in appropriate situations**, given the FunctionalMode
> indicated. Clause 12.5 describes these codes.

三个要点：

- 它是「当前 FunctionalMode 下会生成哪些事件」的**能力清单**，不是「每个事件都会准时到达」的保证；
- 它与 `FunctionalMode` 绑定，能力变化时设备 **shall** 发 `DeviceInfoChanged`（§5.5.1，p.15–16），
  也就是说清单本身可能在会话中变化；
- 它**不区分**事件由主机操作触发还是由机身本地操作触发。

### 2.4 `ObjectAdded 0x4002` 到底承诺了什么

§12.5.2（p.82）的定义是泛化的：

> **EventCode: 0x4002** … Parameter1: ObjectHandle … Desc: A new data object was added to the
> device. The new handle assigned by the device to the new object should be passed in the
> Parameter1 field … If more than one object was added, each new object should generate a
> separate ObjectAdded event.

真正带 "required" 字样的场景只有主机触发的那两个：

- §10.4.14 `InitiateCapture`（p.59–60）：
  > As each of the newly captured objects becomes available, the Responder **is required to send
  > an ObjectAdded event** to the Initiator … This ObjectAdded event **shall contain the
  > TransactionID of the InitiateCapture operation** with which it is associated.
- §10.4.28 `InitiateOpenCapture`（p.69–70）：同一句式，绑定 `InitiateOpenCapture` 的 TransactionID。

**对「用户在机身上按快门」**，1.0 没有任何条款要求必须发 `ObjectAdded`。规范反而在 §12.5.14
（p.86）承认会漏：

> **UnreportedStatus (0x400E)** … This event may be implemented for certain transports where
> situations can arise where the Responder was **unable to report events** … When an Initiator
> receives this event, it is responsible for doing whatever is necessary to ensure that its
> knowledge of the Responder is up to date. This may include re-obtaining individual datasets,
> ObjectHandle lists, etc.

同时 §12.2（p.79–80）也说事件只是「minimal information」，接收方常常需要「post-event
synchronization」。**因此规范层面的正确读法是：`0x4002` 是「尽力通知 + 需要重同步」，
而不是「新照片的可靠信号」。**

**置信度**：高（以上均为原文直引，页码经 PDF 页脚核对）。
**未能验证**：PTP 1.1 / 2013 是否在 §12 增补了「本地拍摄也必须发 ObjectAdded」的措辞——
1.1 正文不可得；1.0 与 1.1 的差异只能从「1.1 全部新增构造向后兼容且可选」这一句
（ISO 15740:2008 Introduction，样本 p.v–vi）间接推断，不足以断言。

## 3. 参考实现怎么做（libgphoto2 / gvfs / Windows）

### 3.1 libgphoto2：通用路径就是中断端点，厂商路径优先私有 RPC

事件总入口是 `camera_wait_for_event`（`camlibs/ptp2/library.c:6649`），它按厂商分流。
真正的取事件函数是 `ptp_check_event`（`camlibs/ptp2/ptp.c:3533`），顺序如下：

1. **Nikon**（`ptp.c:3538-3561`）：先试 `PTP_OC_NIKON_GetEventEx (0x941C)`，再试
   `PTP_OC_NIKON_GetEvent (0x90C7)`。源码注释直说了回退关系：
   > Method offered by Nikon DSLR, Nikon 1, and some older Nikon Coolpix P* … So if we never get
   > events from here, use the ptp "interrupt" method （`ptp.c:3543-3545`）
2. **Canon EOS**（`ptp.c:3564-3569`）：直接 `return PTP_RC_OK`，注释是
   > should not get here ... **EOS has no normal PTP events** and another queue handling.
3. **Canon 消费机**（`ptp.c:3571-3594`）：先发 `CheckEvent (0x9013)`；若没有事件，
   当 `canon_event_mode > 5` 就**不读中断**了：
   > Event Emulate Mode 0 (unset) and 1-5 get interrupt events. 6-7 does not. （`ptp.c:3582`）
4. **其余所有机型**（`ptp.c:3596-3597`）：
   ```c
   /* check the (USB) interrupt based event queue */
   ret = params->event_check(params,&event);
   ```

`event_check` 在 USB 后端是 `ptp_usb_event`（`usb.c:528`），三种模式（`usb.c:523-525`）：
`PTP_EVENT_CHECK`（阻塞等）、`PTP_EVENT_CHECK_FAST`（150 ms 超时，`usb.c:45-48`）、
`PTP_EVENT_CHECK_QUEUE`（0 超时，只看队列）。三者都落到 `gp_port_check_int(...)`
（`usb.c:546-561`），读满 12 字节头后按容器字段解包：

```c
/* if we read anything over interrupt endpoint it must be an event */   /* usb.c:598 */
event->Nparam  = (rlen-12)/4;
event->Code    = dtoh16(usbevent.code);
```

`0x4002` 的处理分两层：

- 栈内部 `handle_event_internal`（`ptp.c:3483`）**只**处理 `DevicePropChanged` 与 `Store*`，
  对 `ObjectAdded` 不做任何事（默认分支空过）——即 libgphoto2 不靠事件维护对象树；
- 对外翻译在 `library.c:7445-7461`：`ObjectAdded` → 取 `GetObjectInfo` → 目录则
  `GP_EVENT_FOLDER_ADDED` + `gp_filesystem_reset`，文件则 `GP_EVENT_FILE_ADDED`。

另外有两处**轮询兜底**，说明上游并不相信事件一定来：

- Nikon 破捕获：`library.c:5927-5929` 注释
  > The Nikon way: **Does not send AddObject event** ... so try to detect it by checking what
  > objects were added.
  随后 `library.c:5930-5978` 用 `GetObjectHandles` 前后差集找新对象，最多 5 轮、轮间 `sleep(1)`。
- Canon 拍摄循环：`library.c:4788-4815` 在 `InitiateCaptureInMemory` 之后持续
  `ptp_check_event`，靠 `ObjectAdded`/`CaptureComplete` 收敛；`library.c:5982-5985` 还记录了
  「Nikon 1 系列有时在 `CaptureComplete` 之后再发 `ObjectAdded`，其它机型顺序相反」。

**函数名澄清**：2.5.34 里**不存在** `ptp_get_event`。等价物是 `ptp_check_event` /
`ptp_wait_event` / `ptp_check_event_queue` / `ptp_get_one_event`（`ptp.c:3596/3612/3511/3630`）。

### 3.2 gvfs：根本不消费相机事件

GNOME 的 gvfs gphoto2 后端（`daemon/gvfsbackendgphoto2.c`，master，2026-11-16 抓取）里
**没有任何 `gp_camera_wait_for_event` 调用**；文件系统监视只服务于本地已缓存目录的
`GFileMonitorEvent`（`:335-399`）。卷的出现/消失靠 udev（`monitor/gphoto2/ggphoto2volumemonitor.c:303`
`on_uevent`）。也就是说：Linux 桌面文件管理器对「相机上多了张照片」的做法是**按需重新枚举**，
不是订阅事件。

### 3.3 Windows / WPD

- MTP v1.1（USB-IF）§4.8（p.36）："**Event support is a mandatory part of MTP.**"
- 微软文档《USB driver》（WIA/STI 内核态 still image 驱动）明确说明支持并暴露 interrupt 端点，
  通过 `DeviceIoControl` / `CreateFile` 访问端口管道。
- **二手**：StackOverflow 上一位开发者转述微软支持回复「interrupt endpoint is required so that
  the driver can receive MTP events from the device」，并称三端点方案「not supported」。
  该转述与我上面引的 SICDD §4.3 一致，但并不因此升格为第一方证据。

**置信度**：libgphoto2 路径 高（源码逐行）；gvfs「不订阅事件」 中高（基于 master 单文件检索，
未能排除其它进程/插件）；Windows 依赖中断端点 中（MTP 规范 + 微软驱动文档可证「端点存在且被用」，
但 WPD 内部对 PTP 相机的具体取事件路径无第一方文档）。
**未能验证**：`wpdmtp.sys` 对纯 PTP（非 MTP）相机是走中断端点还是走厂商 RPC——没有公开实现细节。

## 4. 机型证据：谁真的发 `0x4002`

### 4.1 数据集与口径

libgphoto2 `master` 的 `camlibs/ptp2/cameras/*.txt` 是上游提交的 `gphoto2 --summary` 转储，
里面含完整 `DeviceInfo`（`Manufacturer`/`Model`/`OperationsSupported`/`EventsSupported`）。
我在 2026-11-16 对 466 个文件做了统计（本报告自采，可复现）：288 个能解析出 `Events Supported` 段，
其中 **221 个（76.7%）声明 `0x4002`**。下表按文件名前缀（即上游的品牌命名）聚合：

| 品牌前缀 | 声明 0x4002 / 有清单 |
|---|---|
| canon | 88 / 106 |
| nikon | 76 / 78 |
| fuji | 21 / 21 |
| kodak | 6 / 6 |
| ricoh | 4 / 4 |
| leica | 3 / 3 |
| olympus | 5 / 6 |
| panasonic | 2 / 4 |
| samsung | 2 / 5 |
| **sony** | **2 / 35** |
| apple | 0 / 5 |

> 口径提醒：`EventsSupported` 是**能力声明**（§2.3），不是运行期抓包。下文 §4.3 单列「声明但不发」
> 的反例。同一品牌内部差异极大：Canon 的 106 份里，老 EOS 27/43 声明、新世代 EOS 0/16、
> PowerShot/IXUS 47/49 声明（其余 14 份未归入这两类）——**必须逐机型看 `EventsSupported`，
> 不能按品牌下结论**。

### 4.2 典型清单长什么样

- **Canon EOS R6**（`canon-eos-r6.txt`，Manufacturer 串为 `Canon.Inc`）：`0xC181…0xC191`、`0x4003`、
  `0x4009`，**无 `0x4002`**。而较老的 EOS（`canon-eos5dmark2.txt`、`canon-eos7d.txt`、`canon-eos60d.txt`、
  `canon-eos600d.txt` 等）**多数声明 `0x4002`**（27/43）。`ptp.c:3564` 的注释「EOS has no normal PTP events」
  描述的是运行路径（走 EOS/CheckEvent），与「是否声明 `0x4002`」是两件事。
- **Sony ZV-E10**（`sony-zv-e10.txt`）：`0x4004`、`0x4005`、`0xC201 (Sony_ObjectAdded)`、`0xC202…0xC20D`，
  **无 `0x4002`**。Sony 只有两台老机（`sony-slt-a350.txt` DSLR-A350、`sony-dsc-r1.txt` DSC-R1）
  声明了 `0x4002`。
- **Nikon Z6**（`nikon-z6.txt`）：`0x4001-0x400D` 全套 + `0xC101/0xC102/0xC105/0xC108…`，
  即**同时**声明标准与私有；但 libgphoto2 仍优先 `0x90C7`（`ptp.c:3540`）。
- **FUJIFILM X-T4**（`fuji-xt4.txt`）：`0x4002/0x4003/0x4004/0x4005/0x400D/0xC006`。
- **Panasonic DC-GH5**（`panasonic-gh5.txt`）：标准项里**没有 `0x4002`**，厂商项是 `0xC101-0xC104`；
  而 DMC-GH4 / DMC-GX8 有 `0x4002`。同厂跨代不一致。

### 4.3 「声明」与「真的发」之间的两个反例

1. **Nikon Coolpix**：`library.c` 相机表里 **25 个** Coolpix 型号带 `PTP_NIKON_BROKEN_CAP`
   （首个 `library.c:1436`，末个 `library.c:1631`），配合 `library.c:5927` 的注释
   「Does not send AddObject event」，libgphoto2 直接改成扫 `GetObjectHandles`。
2. **Panasonic 走私有封装**：`ptp.h:1003` 注释
   > `#define PTP_OC_PANASONIC_ChangeEvent 0x9603 /* 2 args ... e.g. 0x4002, new (change object added event) */`
   即标准 `0x4002` 的语义被塞进 vendor 操作里传递；`library.c:7401-7403` 在收到
   `PTP_EC_PANASONIC_ObjectAdded` 时手工改写成 `PTP_EC_ObjectAdded`。

### 4.4 唯一确凿的「真的发 `0x4002`」证据

libgphoto2 issue #569（Nikon 1 V1，**二手机身日志**，非第一方规范）里，主机发完
`InitiateCapture (0x100E)` 后，中断端点读到：

```
gp_port_check_int (3): Read 16 ... from interrupt endpoint
0000 10 00 00 00 04 00 02 40-ff ff ff ff 7e 1a 19 09
ptp (2): event: nparams=0x1, code=0x4002, trans_id=0xFFFFFFFF, p1=0x9191A7E
```

这是「主机触发拍摄 → 中断端点收 `0x4002`」的完整链路证据，且与 §2.4 里
`TransactionID` 的要求对照可见：该机型给的是 `0xFFFFFFFF`（而非 `InitiateCapture` 的
TransactionID），已经属于「不完全符合 §10.4.14」的实现。

**置信度**：能力分布 中高（自采统计 + 上游转储）；「声明 ≠ 发」 高（有上游注释与代码路径）；
「机身本地按快门是否发 `0x4002`」**低**——没有任何公开的系统性抓包。
**未能验证**：Canon 消费机（47 份声明 `0x4002` 的 PowerShot/IXUS）与 Fuji/Olympus 在
**本地拍摄**场景下的 `0x4002` 命中率；这需要真机。

## 5. 与 GetEvent 轮询的关系

### 5.1 标准里没有 GetEvent

- PIMA 15740:2000 全文检索 `GetEvent` / `9116`：**0 命中**（Clause 10 的操作码表到 `0x101C`
  `InitiateOpenCapture` 为止）。
- libgphoto2 2.5.34 `ptp.h` 里 `0x9116` 的定义是
  `#define PTP_OC_CANON_EOS_GetEvent 0x9116`（`ptp.h:428`），另外
  `#define PTP_OC_LEICA_GetViewFinderData 0x9116`（`ptp.h:947`）——同一码在两家是不同操作，
  典型的厂商私有码位复用。
- libmtp `master src/ptp.h` 同样没有标准 `GetEvent`，只有 `PTP_OC_CANON_EOS_GetEvent 0x9116`
  与 `PTP_OC_NIKON_GetEvent 0x90C7`。

所以「主机是否应该轮询 GetEvent」这个问题在 USB 上不成立：**USB 上标准通道只有中断端点**，
`GetEvent` 是厂商在自家扩展命名空间里另开的 RPC。

### 5.2 两条通道能并存吗

能，但实现上是「按厂商择一」，不是「两个都要」：

- Nikon：先私有 `0x90C7`/`0x941C`，**只有拿不到事件时**才落回中断（`ptp.c:3543-3561`，
  且有 `event90c7works` 状态位记住「这家私有通道能用」）；
- Canon：`canon_event_mode > 5` 时不读中断（`ptp.c:3582-3584`），即由相机事件仿真模式决定
  当前生效的是哪条；
- 其余：只走中断。

唯一的「两条通道配合」是 SICDD §5.2.2 的 `Get_Extended_Event_Data (0x65)`：中断先送一个
短事件，主机再发控制请求取附加数据——这是**同一事件的补充读取**，不是队列轮询。

`0x4002` 携带的只是一个 `ObjectHandle`（§12.5.2），要拿到文件名/大小/父目录必须再发
`GetObjectInfo (0x1008)`；libgphoto2 正是这么做的（`library.c:7450-7452`，`ptp_object_want`
按需拉 `ObjectInfo`）。也就是说这条通道**不能**取代轮询，只能减少轮询次数。

**置信度**：高（1.0 全文 + 两个主流库的 opcode 表 + 显式回退代码）。
**未能验证**：ISO 15740:2008/2013 是否正式引入了标准 `GetEvent`（若引入，本节结论需按
「1.1 可选扩展、厂商未实现」调整，而非推翻）。

## 6. 结论与前置条件

### 6.1 值不值得做（按机型分档）

| 档位 | 机型 | 收益 |
|---|---|---|
| **A 有收益** | Nikon Z/DSLR（`0x4002` + `0x90C7` 双路）、FUJIFILM 全系、Olympus E-M5/E-PL 系列、LEICA SL 系列、SIGMA fp、RICOH THETA、GoPro、Kodak | 声明与实现都存在，事件可省掉「每 N 秒扫 `GetObjectHandles`」 |
| **B 无收益** | Canon 新世代 EOS（R 系、M50 及之后、80D/90D、6D Mark II、5D Mark IV）、现代 Sony（A7/ZV/RX）、Panasonic GH5 之后 | 这些机型声明里就没有 `0x4002`（Canon 整体 88/106，但新世代 0/16；老机即便声明也仍走 EOS/CheckEvent），只能走厂商 RPC，通用通道纯属多一个线程 |
| **C 负收益** | 25 个 Nikon Coolpix（`PTP_NIKON_BROKEN_CAP`，上游注释明确「不发 ObjectAdded」） | 连「有新对象」都要靠扫 `GetObjectHandles`，事件通道读到的可能永远是超时 |

### 6.2 工程前置条件（做之前必须先解决）

1. **端点独占**：中断端点的读与 bulk 事务共享同一个 `UsbDeviceConnection`。仓库已经声明了
   `epEv`（`app/src/main/java/cn/devcxl/photosync/ptp/usbcamera/BaselineInitiator.kt:57,138`）
   并有 `readInter()`（`:745-763`，内部 10 次重试），但**没有任何消费方**。接上去要保证
   事件读与 `transact` 串行化，否则会和 `reset()`/`getClearStatus()` 抢连接。
2. **可超时、可取消**：`PTP_EVENT_CHECK_FAST` 的做法值得抄——临时把端口超时调到 150 ms 再读
   （`usb.c:550-556`）。`readInter` 现在的「10 次重试 × timeout」在 UI 线程上会直接卡死。
3. **重同步义务**：收到 `UnreportedStatus (0x400E)`、重连、或会话重建后，必须做一次全量
   `GetObjectHandles`（§12.5.14 的要求）。这条决定了「事件通道」永远需要轮询兜底。
4. **一次往返的成本**：`0x4002` 只给 handle，要 `GetObjectInfo` 才有文件名；突发连拍时
   事件会成串到达，需要合并/去重，不能一事件一往返。
5. **不能只看 `EventsSupported`**：它是能力声明（§2.3），运行时必须以「事件超时 → 降级轮询」
   作为默认路径，而不是「声明了就当可靠」。

### 6.3 什么样本能一锤定音

如果要在 A/B/C 之间做取舍，需要的最小样本是**每厂商 2 台、共约 8 台**：

- Canon 一台**声明了 `0x4002` 的 PowerShot**（如 G9 X / G7 X Mark II，避开 Mark III 与 SX740 HS）；
- Nikon Z6（或 Z 系任一）、FUJIFILM X-T4（或 X-T30）、Sony A7 IV（B 档对照）、
  Olympus E-M5 Mark III、Panasonic GH5（C 档对照）、GoPro HERO、RICOH THETA（A 档对照）。

采集流程（每台 10 分钟）：

1. 抓 `DeviceInfo.EventsSupported`（现有代码已经在打印，`DeviceInfo.kt:119`）；
2. 机身按快门 3 次，同时以 150 ms 超时循环读中断端点 10 s，记录 `EventCode` 与 `Param1`；
3. 主机 `InitiateCapture` 3 次，重复步骤 2；
4. 每次之后做一次 `GetObjectHandles` 增量，作为「真实新增对象」的 ground truth。

**判定线**：本地拍摄场景下 `0x4002` 命中率 ≥ 90% 且相对快门延迟 < 2 s，才把它当「通知」用；
否则只能当「提示」，主路径仍是轮询。若 8 台里 A 档不足 4 台，这条通道的性价比就不成立
（因为 B 档机型本来就要写厂商 RPC，多一套通用通道只是维护面）。

**置信度**：结论方向 中高；「8 台样本够不够」 中（这是最小可判定集，不是统计显著样本）。
**未能验证**：Android USB host 栈在部分机型上对 interrupt IN 端点的 `bulkTransfer` 行为
（仓库现有 `readInter` 用的就是 `bulkTransfer`）是否与 `UsbRequest` 一致——需要在 2–3 台
Android 设备上实测。
